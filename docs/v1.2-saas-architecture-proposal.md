# PRA Talent Intelligence Platform — SaaS Architecture Proposal (v1.2)

**Status:** Approved — architectural blueprint for future development. Approved 2026-07-27, incorporating review feedback (configurable AI-credit entitlements, role-capability permission model, expanded audit scope, reordered roadmap, future-AI extensibility).
**Scope:** Subscription & Billing, Organizations & Teams, Future AI Extensibility, and the recommended build order across Billing/Organizations/Team Management/Permissions/Enterprise/API/Integrations/White-label/Analytics.

---

## 0. Executive summary

| Area | Headline recommendation |
|---|---|
| Tenancy | Keep the existing shared-database, RLS-enforced multi-tenant model. Do not move to per-tenant databases. |
| Organizations | Treat the existing `companies` table as the Organization/tenant boundary. Add a per-company `role` (Owner/Admin/Recruiter/Viewer) and a teammate-invite flow — both currently missing. Do not build sub-team hierarchy yet. |
| Billing | Stripe, per-seat base price + metered AI-credit overage, 4 tiers (Free, Growth, Business, Enterprise). AI-credit allocations are plan-configurable and company-overridable, not hardcoded. Trial is automatic, full-featured, 14 days, no card required. |
| Feature gating | A single `getCompanyEntitlements()` check enforced in server actions (not just hidden in the UI), mirroring the existing RLS-helper-function pattern already used for tenant isolation. |
| Permissions | Role-capability based, not hardcoded role checks — roles map to capability sets in data, so adding a role or adjusting what one can do is a data change, not a code change. |
| Audit logs | Extended to every security-sensitive action platform-wide: invitations, role changes, billing changes, job publishing, candidate status changes, interview scheduling, and material AI-generated actions. |
| Build order | Organizations & Roles → Billing → Analytics Dashboard → Team Management → Permissions hardening → Enterprise → API → Integrations → White-label. |
| Future AI | Entitlement/metering model uses an open, string-keyed usage namespace and capability-based gating specifically so future AI services (Recruiting Copilot, Career Coach, Workforce Analytics, Talent Insights) plug in without architectural redesign. |

The reasoning for each line is below. Section 1 documents what already exists in the codebase today, because several of the "decisions" below are really just recognizing and extending an architecture that's already 80% in place — not choices made from a blank slate.

## 1. Current state assessment

This grounds every recommendation that follows. Skip to Section 2 if you just want the recommendations.

- **Multi-tenancy already exists.** `companies` is the tenant. Every RLS policy on tenant-scoped tables (`jobs`, `applications`, `interviews`, `talent_pool`, `job_matches`, …) filters through `my_company_id()`, a `security definer` SQL function resolving the caller's company via their `recruiters` row. This was hardened in migration `0014_tenant_isolation_rls.sql` after a real cross-company data leak was found and fixed — it is tested (`e2e/rls.spec.ts`) and load-bearing. **This is a shared-database ("pool") multi-tenant model, not silo (DB-per-tenant) or bridge (schema-per-tenant).**
- **Roles today are platform-level, not org-level.** `profiles.role` is an enum: `candidate | recruiter | hr_manager | super_admin`. This says what *kind* of user someone is platform-wide, not what they can do *within a specific company*. The only per-company signal is `recruiters.is_company_admin`, a single boolean — binary admin/non-admin, no intermediate roles.
- **There is no teammate-invite flow.** `registerRecruiter()` (`src/actions/auth.ts`) always creates a **brand-new company** on signup and sets the registrant as `is_company_admin: true`. There is no path today for a second person to join an *existing* company. Every recruiter account is, today, a company of one. This is the single biggest gap standing between the current app and any real "Team Management" feature.
- **Audit logging exists but is admin-only.** `audit_logs` (migration `0008`) is a real table with a shared write helper (`src/lib/audit.ts`), used exclusively by super-admin panel actions. No recruiter-initiated action (job published, application status changed, interview scheduled, teammate invited) writes to it, and there is no company-scoped read UI for it — only the platform admin panel reads it.
- **No billing, plan, or entitlement schema exists anywhere.** No Stripe (or any payment provider) dependency in `package.json`. No `plan`/`tier` column on `companies`. No usage-counter table. This is fully greenfield.
- **Ownership today is already effectively org-level, not individual-level**, even without explicit modeling: `jobs.recruiter_id` records *who created* a job, but RLS grants every recruiter at the same company full visibility and management rights over all of that company's jobs/candidates/applications. This is good — it means "Organization owns the data" is already the de facto model and needs no migration, just formalizing.

## 2. Subscription & Billing

### 2.1 Pricing model recommendation

**Recommendation: per-seat base price + metered AI-credit overage (hybrid), not flat-rate and not pure usage-based.**

| Model | Description | Trade-off |
|---|---|---|
| Flat-rate (one price, unlimited use) | Simplest to build and explain. | Leaves money on the table with heavy users; gives no natural lever to price Enterprise higher; doesn't map to the app's real cost driver. |
| Pure usage-based (pay per AI call, per job posting, etc.) | Cost tracks usage tightly; attractive for very light users. | Unpredictable bills scare B2B buyers; procurement teams dislike variable-cost line items; harder to sell as a fixed "seats" package internally at the customer. |
| Per-seat only | Familiar SaaS model (Slack, Notion-style); predictable for both sides. | Doesn't capture value from AI-heavy usage (a 3-recruiter team running the AI Interview Assistant constantly costs far more in OpenAI spend than a 3-recruiter team that barely uses AI features, but would pay the same). |
| **Per-seat + metered AI-credit overage (recommended)** | Predictable base price familiar to buyers, with a usage lever specifically on the feature that actually drives marginal cost (OpenAI API calls). | More billing logic to build (usage counters, overage invoicing) than flat-rate. Still, this is the standard AI-SaaS pattern for good reason. |

**Why AI credits specifically, and not job postings or candidates as the usage axis:** every AI feature shipped so far (resume parsing/ATS scoring, job matching, screening, AI Resume Builder suggestions, AI Interview Assistant question generation, Recruiter AI Assistant job/message drafts) is a discrete, metered OpenAI API call with a real per-call cost. Job postings and candidate records, by contrast, cost the platform almost nothing to store. Metering the thing that actually costs money, rather than a proxy for it, keeps the pricing model honest and future-proof as more AI features ship.

**Recommended tiers:**

| Tier | Seats | AI credits/mo (included) | Target |
|---|---|---|---|
| Free | 1 | Small fixed allotment (e.g. enough for ~5 job postings' worth of screening/matching) | Solo recruiters, evaluation |
| Growth | Up to 5 | Mid allotment + pay-as-you-go overage | Small teams, the primary paid tier |
| Business | Up to 25 | Higher allotment + overage, priority support | Growing companies |
| Enterprise | Custom | Custom/negotiated | Large orgs, see 2.5 |

### 2.2 Feature gating strategy — configurable, overridable entitlements

**Recommendation: gate in the server action layer, not just the UI, via a single `getCompanyEntitlements(companyId)` check — and make every entitlement (AI credits especially) plan-configurable and company-overridable by data, not hardcoded by tier in code.**

The codebase has an established, proven pattern for this exact class of problem: `is_candidate_visible_to_staff()` and `my_company_id()` are single security-definer functions that every relevant policy/action calls, so a rule only has to be right in one place. Entitlements follow the same shape: one function, called at the top of every gated server action (`generateInterviewQuestionsForJob`, `generateMatchesForJob`, `draftJobDescription`, `draftCandidateMessage`, `createJob`, etc.), returning what the company's current plan allows and how much it's already used. Gating only in the UI (disabling a button) is not real gating — it's trivially bypassed by calling the server action directly, and this codebase's own RLS-leak history (migration 0014) is a direct lesson in why app-layer-only enforcement isn't sufficient on its own.

**Two-layer resolution, not hardcoded tier constants:**

1. **`plan_defaults`** — `(plan_tier, metric_key, included_amount, overage_price)`. `metric_key` is a free-text key, not a fixed enum column — this is the design choice that makes the whole system extensible (see Section 5). Changing what Growth includes, or adding a new metered resource, is a data change to this table, not a code deploy.
2. **`company_entitlement_overrides`** — `(company_id, metric_key, override_amount)`, nullable. When a row exists for a company+metric, it supersedes the plan default entirely. This is the direct mechanism for "AI credits configurable per company" — an Enterprise customer negotiating a custom AI-credit ceiling (or a support team comping a struggling customer extra credits for a month) is one row insert, not a special-cased code path.

`getCompanyEntitlements(companyId)` resolves: override if present, else plan default. Every gated action calls this one function; nothing else needs to know whether a given company is on a standard plan or a custom deal.

**What gates on plan, and how hard:**

| Resource | Gate type | Reasoning |
|---|---|---|
| AI credits | Hard block once exhausted, with clear upgrade/buy-more prompt | Real, uncapped dollar cost if left ungated — this is the one resource where a hard stop is non-negotiable. |
| Seats (active recruiters) | Hard block on invite beyond plan limit | Billing integrity — an unpaid extra seat is invisible revenue leakage, and this is also the actual metric Stripe subscription quantity should track. |
| Active job postings | Soft limit: warn + prompt upgrade, allow a short grace period | Doesn't cost the platform much per extra posting; hard-blocking a company mid-hire is a bad customer experience for a low-cost resource. |
| Advanced AI features (AI Interview Assistant, Recruiter AI Assistant, cross-pool candidate discovery) | Capability-gated (see Section 3.3) rather than metered | These are more differentiators than cost centers per se; gating by capability is simpler to sell ("upgrade to unlock") than metering each separately, and reuses the same capability mechanism as role permissions instead of a parallel system. |
| Talent pool / candidate database size | Soft limit, tier-gated ceiling | Storage is cheap; this is more a segmentation lever than a cost-control one. |

An admin-facing screen to manage `company_entitlement_overrides` per company is a natural, low-cost extension of the existing super-admin settings infrastructure (`SettingsSectionForm` already provides the form pattern) — no new UI paradigm needed.

### 2.3 Trial model

**Recommendation: automatic, full-featured, 14-day trial, no credit card required, auto-downgrade (not lockout) at expiry.**

| Model | Trade-off |
|---|---|
| No trial, pay upfront | Kills the self-serve motion the app already has (registration is instant today, zero friction) — would be a regression in conversion. |
| Credit-card-required trial | Higher-intent signups, lower volume; better fit for higher-ACV Enterprise motion than a self-serve product. |
| **Card-optional, full-featured trial (recommended)** | Maximizes signups and lets people actually feel the AI features (which are the product's differentiator) before deciding; the risk is trial abuse via disposable accounts, mitigated by the existing per-IP rate limiting already in `rateLimitByIp` plus per-account AI-credit caps even during trial. |
| Freemium-forever (no trial, just a permanent free tier) | Removes urgency to convert; the Free tier above already covers "let people use it forever at a small scale" without needing a separate concept. |
| Reverse trial (start on paid tier, downgrade to free after N days) | More aggressive, higher conversion in some products, but a bigger UX surprise for a first-time signup; not recommended until there's data suggesting the softer approach underconverts. |

Trial should start automatically at company creation (no separate "start trial" button) to match the zero-friction registration flow that already exists. At expiry, auto-downgrade to Free rather than lock the account — losing access entirely is a common cause of silent churn and support tickets; a graceful downgrade keeps the account (and its data) reachable for a later upgrade.

### 2.4 Usage limits

**What to meter:** AI credits (dominant cost driver, see 2.1), seats, active job postings, resume/candidate storage (soft).

**Implementation shape:** a `usage_counters` table (`company_id`, `metric_key`, `period_start`, `count`), keyed by the same open `metric_key` namespace as `plan_defaults` (Section 2.2) — not a fixed enum. Incremented at each AI-call site. This is a small addition — every AI-generating action already exists as a clean, single-purpose function (`generateMatchesForJob`, `runAIScreening`, `generateInterviewQuestions`, `generateJobDescriptionDraft`, `generateCandidateMessage`, etc.), so metering is a matter of wrapping each call site, not restructuring the AI layer. A monthly reset (cron or lazy period-rollover on read) resets counts.

**Hard vs. soft, recap:** hard-block only where real money or billing correctness is at stake (AI credits, seats); soft-limit-with-upgrade-prompt everywhere else. This mirrors 2.2's gate-type table.

### 2.5 Future enterprise support

Don't build Enterprise-specific infrastructure now (see roadmap, Section 4) — the `plan_defaults` + `company_entitlement_overrides` design in Section 2.2 already ensures an Enterprise deal never requires a schema change. A custom Enterprise contract (raised AI-credit ceiling, unlimited seats, custom terms) is a data change — an override row — not a code change, from day one, even before SSO/SAML, dedicated support tooling, or custom SLAs are actually built. Enterprise as a tier is really just "a company that's expected to have override rows"; the mechanism itself is general-purpose and already serves every plan, not an Enterprise-only escape hatch.

## 3. Organizations & Teams

### 3.1 Single-tenant vs. multi-tenant recommendation

**Recommendation: continue the existing shared-database, RLS-enforced multi-tenant model. Do not move to single-tenant (database- or schema-per-customer).**

| Model | Trade-off |
|---|---|
| Silo (dedicated database per tenant) | Strongest isolation and easiest "your data lives on its own instance" enterprise story, but massive operational overhead (migrations run N times, N connection pools, N backups) — completely disproportionate to a self-serve SaaS motion, and a ground-up rebuild of everything shipped so far. |
| Bridge (dedicated schema per tenant, shared database) | Middle ground, still meaningful migration/ops overhead per tenant; same rebuild cost as silo for this codebase since nothing today is schema-per-tenant aware. |
| **Pool (shared tables, RLS-enforced isolation) — current and recommended** | Lowest ops overhead, scales to thousands of tenants on one database, and is *already built and tested* (migration 0014's fix plus `e2e/rls.spec.ts`'s isolation tests). The only real risk is a policy bug re-leaking data across tenants — mitigated by keeping the "one security-definer helper function per access rule" discipline already established, and by the existing automated RLS test suite. |

If a specific future Enterprise customer contractually requires physical data isolation, that's solvable later as a one-off (e.g., a dedicated read replica or a data-export/residency arrangement) without redesigning the whole platform now on the *chance* one customer asks.

### 3.2 Organization hierarchy

**Recommendation: `companies` = Organization, full stop, for now. Do not add sub-team/department entities yet.**

The schema already has a free-text `department` field on `jobs` and `recruiters` — enough for labeling and filtering, not enough (nor should it be, yet) for permission boundaries. Building a `teams` table with its own membership and job-ownership scoping is a real feature with real complexity (job.team_id, team-scoped RLS, UI to manage it) — and there is no evidence yet that any customer needs it, since the platform doesn't even have multi-person companies today. Building hierarchy speculatively, before a single real company has more than one recruiter, risks the exact kind of premature abstraction this project has deliberately avoided elsewhere (see the `AI_ELIGIBLE_SECTION_TYPES` and merge-diff scoping decisions in the AI Resume Builder phase). Revisit sub-teams once Business/Enterprise customers with 25+ recruiters actually ask for department-level job/candidate segregation.

### 3.3 Roles and permissions — role-capability based, not hardcoded role checks

**Recommendation: a fixed 4-role set (Owner / Admin / Recruiter / Viewer) whose actual permissions are expressed as a data-driven mapping from role → capabilities, not scattered `role IN (...)` checks.**

| Approach | Trade-off |
|---|---|
| Keep current binary `is_company_admin` | Insufficient the moment a company has more than 2 people — no way to have a "can post jobs but not manage billing" role, which real hiring teams need almost immediately. |
| Fixed roles, hardcoded checks (`role IN ('owner','admin')`) everywhere a rule applies | Simple to write, but every RLS policy and server action that cares about permissions embeds the role list directly — adding a 5th role, or changing what Viewer can do, means hunting down and editing every one of those check sites. This is exactly the kind of duplicated-rule risk that caused the real tenant-isolation leak fixed in migration 0014, just for permissions instead of tenancy. |
| **Fixed roles, capability-based checks (recommended)** | Same 4 roles, same user-facing simplicity, but every check site asks "does this role have capability X?" against a data table, not "is this role literally named Owner or Admin?". Adding a role, or moving a capability from one role to another, is a data change. Slightly more upfront design (defining the capability vocabulary) than hardcoding, but this is a one-time cost. |
| Fully custom RBAC (admin-defined permission matrix per org) | Maximum flexibility, but this is an Enterprise-tier feature in most SaaS products for a reason: it's complex to build, complex to audit, and most customers never touch the defaults anyway. The capability model below is what makes this reachable *later* without a rewrite, without needing to build it now. |

**Roles** (unchanged from the original proposal):

- **Owner** — exactly one per organization; full control including billing and the ability to delete the org; cannot be removed, only reassigned (see 3.6).
- **Admin** — manage team members, jobs, and org settings; cannot touch billing or transfer ownership.
- **Recruiter** (default) — full read/write on jobs, candidates, applications, interviews within the org; today's `is_company_admin: false` recruiter, formalized.
- **Viewer** — read-only; for hiring managers or interviewers who need visibility into candidates/interview feedback but shouldn't edit job postings or applications.

**Capability model:**

- A fixed vocabulary of capability strings: `manage_billing`, `manage_org_settings`, `invite_members`, `remove_members`, `change_member_roles`, `manage_jobs`, `view_jobs`, `manage_candidates`, `view_candidates`, `schedule_interviews`, `submit_interview_feedback`, `use_ai_features`, `view_analytics`, plus room to grow (`manage_integrations`, etc., added later without touching existing rows).
- A `role_capabilities` mapping table (`role`, `capability`), seeded with each of the 4 roles' defaults — e.g. Viewer gets `view_jobs` + `view_candidates` + `view_analytics` only; Recruiter gets everything except `manage_billing`/`manage_org_settings`/member management; Admin gets everything except `manage_billing`; Owner gets everything.
- A single security-definer SQL helper, `public.has_capability(capability text) returns boolean`, following the exact shape of `is_staff()`/`is_admin()` already in the codebase: it resolves the caller's `recruiters.role`, looks it up against `role_capabilities`, and returns whether the capability is granted.
- Every RLS write policy and every gated server action calls `has_capability('manage_jobs')` (etc.) instead of embedding role names. `is_company_admin` is dropped in favor of the new `role` column + capability table, rather than kept as a second, potentially-disagreeing source of truth.
- **Consistency with Section 2.2:** this mirrors the plan-defaults + company-overrides shape used for billing entitlements — a base mapping (`role_capabilities`, analogous to `plan_defaults`) that could later support a per-company capability override table (analogous to `company_entitlement_overrides`) if a specific Enterprise customer needs a bespoke tweak (e.g., "our Viewers should also be able to schedule interviews"), without rebuilding the permission system to get there.

### 3.4 Recruiter collaboration

**Recommendation: ship a teammate-invite flow — the single highest-leverage missing piece — and defer richer collaboration features (comments, @mentions, assignment) until there's real multi-person usage to learn from.**

Today, shared visibility within an org already works (RLS scopes by `company_id`, so any recruiter at a company already sees all of that company's jobs/candidates once they exist there) — what's missing is *getting a second person into the company at all*. The invite flow should reuse the exact pattern already proven in `registerRecruiter()` (admin-client `createUser` with `email_confirm: true`, bypassing the broken default-mailer confirmation flow): an Admin/Owner enters a teammate's email + role, the system creates (or attaches, if the email already has an account) a `recruiters` row scoped to the existing `company_id` instead of minting a new company, and sends an invite email once real email infrastructure exists (see the Recruiter AI Assistant phase note that no email-sending exists yet — this is the first feature that will actually require it, and is a reasonable trigger to finally add it).

Deliberately out of scope for v1: in-app comments/notes threading, @mentions, and formal candidate "assignment" to a specific recruiter. `talent_pool.notes` already gives lightweight free-text collaboration; richer threaded collaboration is a real feature but not a blocker for teams to function.

### 3.5 Audit logs — every security-sensitive action, platform-wide

**Recommendation: extend the existing `audit_logs` table and `logAudit()` helper to every security-sensitive recruiter-initiated action, and add a company-scoped read view. No new schema needed.**

This is unusually cheap to do well because the infrastructure already exists and works — it's just only wired to admin actions today. Required coverage:

| Category | Logged actions |
|---|---|
| Invitations | Teammate invited, invite accepted, invite revoked, member removed |
| Role changes | Recruiter role changed (old role → new role), ownership transferred |
| Billing changes | Plan changed (upgrade/downgrade), payment method updated, subscription cancelled, entitlement override added/changed by an admin |
| Job publishing | Job published, archived, closed |
| Candidate status changes | Application status changed (submitted → screening → shortlisted → interview → offer → hired/rejected) |
| Interview scheduling | Interview scheduled, rescheduled, cancelled, feedback submitted |
| AI-generated actions (where appropriate) | AI screening run, AI match generated, AI interview questions (re)generated, AI job description drafted, AI candidate message drafted |

**Why AI actions are in scope, not just human ones:** algorithmic hiring decisions are under increasing regulatory scrutiny — NYC Local Law 144 requires bias-audit disclosure for automated employment-decision tools, and the EU AI Act treats employment-related AI as high-risk. Logging *that* an AI screening/match/question-generation ran, on which application/job, with which model, at what time, is exactly the kind of trail that makes "why did the AI score this candidate this way" answerable later, whether the question comes from a candidate, a regulator, or an internal review. This doesn't need full prompt/response payloads in the log (those already live on the underlying `screening_results`/`job_matches`/`interview_questions` rows) — the audit entry just needs enough metadata (entity type/id, model, timestamp, actor if human-triggered) to reconstruct the decision trail.

Add an RLS select policy scoping `audit_logs` reads to `actor`'s company for non-admins, and a simple "Activity Log" page under `/recruiter/settings` (or a new `/recruiter/activity`) reusing the admin audit-log UI patterns. This should ship alongside Team Management (Section 4) since "who invited whom, who changed what role" is exactly the kind of action a company Owner will want visibility into immediately.

### 3.6 Ownership model

**Recommendation: formalize what's already implicit — the Organization owns the data, not the individual recruiter; billing is owned at the org level; exactly one Owner per org.**

- **Data ownership:** already org-level in practice (RLS scopes by `company_id`, not `recruiter_id`) — `jobs.recruiter_id` remains useful as "who created this" metadata but should never be an access-control field. No change needed here beyond documenting it as an explicit invariant.
- **Billing ownership:** one Stripe customer per organization (`companies.id`), never per recruiter — a company's subscription must survive any individual recruiter (including the original founder) leaving.
- **The Owner role:** exactly one per org at all times. Maps directly to today's company-creating registrant. Cannot be deleted/demoted directly — must transfer ownership to another Admin first (a two-step "propose transfer → accept" flow is the safe pattern, avoiding an org ever being left ownerless by a mistaken single action).

## 4. Product roadmap — recommended implementation order

| # | Item | Depends on | Why here, not earlier/later |
|---|---|---|---|
| 1 | **Organizations & Roles** (Section 3.3, 3.4: role/capability schema, invite flow) | Nothing new — extends existing `recruiters`/`companies` schema | Everything else in this document assumes companies can have more than one member with differentiated permissions. Billing can't count "seats" meaningfully, and Analytics has limited org-level data to show, until this exists. This is the true foundation. |
| 2 | **Billing** (Section 2) | #1 (seats must be countable) | Once orgs can have real teams, seat-based pricing becomes meaningful and testable. Doing billing before this would mean building seat-counting twice. |
| 3 | **Analytics Dashboard** (per-org recruiter dashboards: pipeline funnel, time-to-hire, AI-credit usage; platform-wide admin analytics) | #1 (org-scoped operational data) and #2 (usage/billing data — AI-credit consumption, seat utilization become dashboard content once metered) | Moved up from its original "opportunistic" slot: analytics needs org data and usage data, not a finished Team Management UI or hardened permission model, so this reordering is dependency-safe. It's also the fastest way for a customer to *see* the platform's value (pipeline velocity, AI usage paying for itself) immediately after paying for it — directly supports retention right after the moment of highest churn risk (right after purchase). |
| 4 | **Team Management UI** (invite/remove members, role assignment, activity log) | #1 (schema/actions), benefits from #2 (enforcing seat limits at invite time) | The *backend* for this ships in #1; this is the polished user-facing surface plus wiring it to billing's seat limits so invites over the seat cap are properly gated. |
| 5 | **Permissions hardening** (Viewer restrictions across every existing surface, e.g. hiding Schedule/Feedback/Draft-message actions from Viewers) | #1 | Deliberately *after* Team Management ships and is used for a bit — real usage will surface which of the 4 roles' boundaries actually matter in practice versus which are theoretical, avoiding over-building permission checks nobody needs. The capability model from 3.3 makes this cheap whenever it happens. |
| 6 | **Enterprise features** (SSO/SAML, capability/entitlement overrides in the admin UI, dedicated support tooling, audit-log export) | #2 (billing tier), #5 (permission model to layer SSO-provisioned roles onto) | No customer to build these *for* yet; Sections 2.5 and 3.3 already ensure the plan/permission schema won't need rework when this is eventually needed. Building SSO before there's a single paying Enterprise customer is speculative cost with no validation. |
| 7 | **API** (public REST/GraphQL for external integrations) | #1 and #5 (need a stable, real permission model to expose externally — an API is a second, harder-to-patch attack surface for any permission bug) | An API is a commitment (versioning, backward compatibility, docs, rate limiting) that's expensive to get wrong. Should follow, not lead, a settled internal permission model. |
| 8 | **Integrations** (calendar sync for interviews, Slack notifications, job-board syndication, HRIS/ATS import-export) | #7 for anything third-party-facing; some (e.g. calendar sync for the interview scheduler shipped in the AI Interview Assistant phase) could be a direct one-off integration built without waiting for a general API | Most integrations are naturally API consumers or producers; building them before the API exists means either duplicating auth/webhook plumbing per integration or blocking on #7. A couple of high-value one-offs (calendar invites, in particular, since interview scheduling already exists) could jump the queue as bespoke work if there's demand pressure. |
| 9 | **White-label** (custom domain, branding, remove PRA branding) | #2 (this is realistically an Enterprise/Business-tier paid feature) and #3.2's org model (branding is an org-level setting) | Highest build cost relative to near-term value — custom domains alone involve DNS/SSL/multi-tenant routing complexity — and there's no evidence of demand yet. Should wait for a specific customer/deal that justifies it, consistent with the Enterprise philosophy in Section 2.5 and #6 above. |

**One-line summary of the ordering logic:** build the org/role foundation first (nothing else makes sense without it), monetize it next (billing), show customers the value immediately via analytics, then build out the team-facing surface and harden permissions with real usage data, and treat Enterprise/API/Integrations/White-label as demand-driven additions that come after — not before — there's a real paying, multi-person customer base to build them for.

## 5. Future AI services & platform extensibility

Reserving room for future AI-powered services — **AI Recruiting Copilot**, **AI Career Coach**, **AI Workforce Analytics**, **AI Talent Insights** — without a later architectural redesign. None of these are being scoped or built now; this section defines the two design commitments elsewhere in this document that specifically exist to keep the door open for them.

**How each plausibly fits, at a glance:**

- **AI Recruiting Copilot** — a broader, more conversational evolution of today's Recruiter AI Assistant (Section 4 background: job posting writer + message drafts). Same billing unit (company), same user (recruiter) as everything shipped so far — the most natural fit of the four.
- **AI Workforce Analytics** and **AI Talent Insights** — aggregate, cross-hire intelligence (pipeline trends, market/benchmarking signals). These are analytics-adjacent AI products layered on top of the Analytics Dashboard's data (Section 4, item 3) — which is part of why moving Analytics earlier in the roadmap has a second benefit beyond immediate customer value: it also lays the groundwork these two future services would build on.
- **AI Career Coach** — candidate-facing (mock interviews, career guidance, resume/profile coaching). This one is structurally different from the other three and is called out separately below.

**Design commitment 1 — the usage/metering namespace is open, not fixed.** Section 2's `plan_defaults`, `company_entitlement_overrides`, and `usage_counters` all key on a free-text `metric_key`, not a Postgres enum or a hardcoded set of columns. Adding `ai_recruiting_copilot_turns` or `ai_workforce_analytics_reports` as a new metered dimension later is a new constant in code plus new rows in `plan_defaults` — zero schema migration, zero changes to the entitlement-resolution logic itself.

**Design commitment 2 — capability gating is equally open.** Section 3.3's `role_capabilities` model works the same way: a new AI feature needs a new capability string (e.g. `use_recruiting_copilot`) and a seed row per role, not new hardcoded checks scattered through RLS policies and server actions. The same override mechanism that lets an Enterprise customer get a custom AI-credit ceiling (Section 2.5) lets one get early/exclusive access to a new AI capability, using the identical pattern.

**Open question, flagged rather than resolved here: AI Career Coach is candidate-facing, and candidates don't have a billing relationship today.** Every entitlement/billing concept in this document is scoped to `companies` — candidates are a structurally separate part of the schema, related to companies only indirectly through applications and matches, never a tenant with a plan of their own. A candidate-facing AI product doesn't fit the company-plan model as designed, and shouldn't be forced into it prematurely. Three real options exist and deserve their own decision when this is actually scoped:

1. **A separate candidate-side subscription** — its own plan/entitlement system, parallel to but distinct from the company-side one.
2. **An employer-sponsored perk** — Business/Enterprise companies can offer AI Career Coach to their applicants as a candidate-experience benefit, billed to the company's plan (extending, not replacing, the existing model).
3. **An always-on limited free tier** — a growth/acquisition lever, the same role the Guest ATS Checker already plays today as a no-account entry point into the platform.

No recommendation is made between these three now — the right answer depends on product strategy at the time Career Coach is actually scoped, not on anything architectural. What matters for this document is that the billing model above doesn't need to guess right about this today; it just needs to not preclude any of the three later, which it doesn't.
