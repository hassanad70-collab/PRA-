# Job Seeker Product Expansion Proposal (v1.3 — Design Only)

**Status:** Approved — official Job Seeker Product Expansion Blueprint.
**Product positioning (binding, not a slogan):** PRA is **an AI-powered Career Intelligence Platform for both Job Seekers and Recruiters** — not a TopResume clone, and not a job-seeker-only pivot. Every feature in this document is evaluated against whether it strengthens that positioning, not simply whether a competitor has an equivalent. Where a TopResume feature doesn't fit that identity (Section 6), it's left out on purpose.
**Constraint carried over from the approved roadmap:** Billing (Stripe) and the rest of the SaaS roadmap (Team Management UI, Permissions hardening, Analytics, Enterprise, **API**, Integrations, White-label) are still sequenced as previously approved. Nothing in this proposal jumps ahead of that ordering — see Section 3.3's note on "API additions."

## 1. Existing PRA Job Seeker capabilities (grounded inventory)

Everything below was confirmed directly against the current codebase, not assumed:

- **Profile & data model:** `candidates` + `candidate_experience/education/skills/certificates/languages/projects/achievements/social_links` — a full structured profile, already the reusable "unified candidate profile" primitive (per `getCandidateFullProfile`).
- **Resume upload + AI parsing:** `resumes` table, `src/lib/ai/resume-parser.ts`, `src/lib/ai/extract-text.ts` — uploads get parsed into `ParsedResumeData` automatically.
- **ATS scoring:** `src/lib/ai/ats-scorer.ts` → `ats_scores` table → `AtsScoreCard` component. Already produces: overall score, 6 sub-scores (experience/skills/formatting/education/achievements/recruiter-readability), keyword density, weaknesses, and suggestions. This is a real, working AI Resume Score Dashboard in substance — just not framed or surfaced as its own page.
- **AI resume improvement:** `src/lib/ai/resume-improver.ts` → `improveResumeAction` → `ImproveResumeDialog`. One AI call already returns: rewritten summary, rewritten bullets per role, missing-skill suggestions, ATS keywords to add, grammar fixes, and generated achievement statements — **entirely ephemeral today**, nothing is persisted or applied back to the profile/resume.
- **AI Resume Builder** (shipped earlier this engagement): `resume_drafts`/`resume_draft_sections`, section-by-section AI suggestions with accept/reject, PDF/DOCX export. This is a *second*, separate resume-editing system from the upload-based one above — the expansion below reuses both rather than building a third.
- **AI job matching:** `job_matches` (pgvector-based), surfaced as match badges, a full match breakdown (strengths/missing skills/AI summary) on job detail pages, and a dashboard "recommended jobs" widget.
- **Applications & interviews:** `applications`, `interviews`/`interview_questions` (candidate sees scheduled interview info read-only, from the AI Interview Assistant phase).
- **Career Dashboard (lightweight, already live):** `/candidate/dashboard` — profile completion %, active application count, resume count, latest ATS score, AI-recommended jobs, recent applications.
- **Guest ATS Checker:** a public, no-account instant ATS scan — already PRA's version of "free resume review," and notably *faster* than TopResume's own free review (their "Free Resume Review" is a human-in-the-loop service with a 48-hour turnaround, confirmed directly from their site; PRA's is instant).
- **Dormant, unused schema worth activating rather than re-creating:** `cover_letters` (only ever holds free-text entered at application time, no AI generation) and `portfolio_items` (title/description/file_url/link_url per item — zero code references it anywhere). Both are exactly the shape needed for two of the target items below, at zero migration cost.
- **A stale marketing listing worth a free fix:** `src/lib/marketing/ai-tools.ts` still lists `resume_builder` as `"coming-soon"` even though it shipped and is fully live — and already lists `cover_letter_generator`, `interview_prep`, and `career_advisor` as `"coming-soon"` placeholders, meaning the public site already promises three of this proposal's target items.

## 2. TopResume competitive analysis (grounded in a live check of their site)

TopResume's public offering, confirmed directly (topresume.com, "18 Powerful Career Tools" page, "Free Resume Review" page) rather than assumed from memory:

| TopResume capability | PRA equivalent / gap |
|---|---|
| AI Resume Builder + 100s of visual templates | PRA has an AI Resume Builder; template *variety* is currently a single layout (PDF/DOCX export) — not on the user's 24-item target list, noted only as a minor observation, not a build item here. |
| Cover Letter Builder | Gap — Section 5, Unit B. |
| Job Board (aggregated listings) | PRA's own job board + AI matching is arguably the stronger version of this (real semantic matching, not board aggregation) — not a gap. |
| Job Tracker (kanban-style saved jobs by stage) | PRA has `saved_jobs` + `applications` with status; not visualized as a kanban board — folded into Unit H. |
| **Auto Apply** (applies to jobs on the candidate's behalf) | **Not recommended.** This implies automated scraping/submission against third-party job boards' own terms of service, plus real risk of submitting incomplete/wrong applications unsupervised. Not on the user's target list either — flagging that it should stay out of scope, not a silent gap. |
| Salary Analyzer | Gap — Section 5, Unit E (AI-estimated ranges, provider-agnostic architecture — resolved, no external data source in v1). |
| Interview Prep / simulator | PRA's AI Interview Assistant generates interview *questions*, but for the **recruiter** to run, not a candidate-facing self-practice tool. Distinct from PRA's existing feature, not a duplicate — but not on the user's 24-item list either, so not built here; flagged as a natural future addition. |
| Resume Distribution (to a recruiter network) | PRA's opt-in AI candidate discovery (from the AI Resume Matching phase) is the same idea, done with real semantic matching rather than blanket distribution — not a gap. |
| Unlimited Learning (400+ licensed courses) | Third-party content licensing, a business decision, not on the target list — out of scope. |
| 1:1 human coaching / resume writing / "Get Hired Now" | Human services, not applicable to an AI-only self-serve product — **AI Career Coach** (Section 5, Unit D) is the AI-native analog. |
| Career Planning | **AI Career Roadmap** — Unit D. |
| Free Resume Review ("what does the ATS see") | PRA's Guest ATS Checker already matches this, and is faster (instant vs. 48 hours). Not a gap. |

**Read on the comparison overall:** PRA's differentiators — real pgvector-based matching (not board aggregation), an instant automated ATS check (not a 48-hour human queue), and a genuine multi-tenant recruiter side TopResume has no equivalent of at all — are real advantages worth preserving, not diluting. TopResume is a job-seeker-only product; PRA is not, and never should become one by imitation. This table exists to find *gaps in candidate value*, not to set TopResume's feature list as the target — every gap closed below is closed in a way that also strengthens the recruiter side (Section 5's "Resume Intelligence" unification and Section 8's future-capability list both deliberately connect job-seeker features to the recruiter/company side of the platform, not just to each other).

## 3. Cross-cutting considerations (apply to every build unit below)

### 3.1 AI credit metering — every new AI action must be metering-ready, even though metering isn't wired up yet

Billing (Stripe) is approved but not implemented (blocked on real credentials, per the standing instruction). Every new AI-generating function in this expansion must still be written as a **single, clean, independently-callable function** (the pattern every existing AI module already follows — `resume-improver.ts`, `ats-scorer.ts`, `job-matcher.ts`, etc.) specifically so a `consumeAiCredits(companyId-or-candidateId, metricKey)` call can be inserted at the top of each one later, without restructuring, exactly as the approved SaaS blueprint's Section 5 ("Future AI services & platform extensibility") already promises. Concretely: no new AI feature should be built as an inline chunk of a larger action — it should be its own function in `src/lib/ai/`, callable on its own.

### 3.2 i18n scope — resolved: the candidate portal becomes fully multilingual, starting with a prerequisite migration

**Decision (binding):** the Candidate Portal is no longer an exception to PRA's i18n architecture. Every new Job Seeker feature in this proposal ships with full English/Arabic support and RTL-correct layout from day one — the same standard as the public site, not a reduced one.

This is a bigger change than "translate the new pages," and it needs to be named honestly rather than understated: today, `/candidate/*` (like `/recruiter/*` and `/admin/*`) is **deliberately outside** the locale-prefixed `[locale]` route tree — `src/middleware.ts`'s `EXCLUDED_PREFIXES` list excludes it on purpose, and every existing candidate page is plain English with hardcoded strings (the precedent recorded in this project's own `i18n_architecture_gotchas` memory). "Fully multilingual, exactly like the rest of PRA" means candidate routes need to actually join the locale-prefixed architecture (`/en/candidate/...`, `/ar/candidate/...`, hreflang, RTL logical properties, translated message catalogs) — not just have their visible text swapped out while keeping an English-only URL structure that no other translated part of PRA uses.

Building eight new feature units on top of an English-only foundation and retrofitting locale support afterward would mean doing the same migration work twice. **This proposal therefore adds a new prerequisite, Unit 0, that must land before any of Units H/A/B/C/D/F/G/E** — every subsequent unit is then built directly inside a fully internationalized candidate portal, the same way every public-page feature already is.

#### Unit 0 — Candidate Portal Internationalization (prerequisite)
**What it does:** migrates the existing candidate route tree into the same locale-prefixed architecture as the public site, and establishes the translation/RTL foundation every new feature in this proposal builds on.
**DB changes:** none.
**AI changes:** none.
**Routing/architecture changes:**
  - Move `/candidate/*` inside `[locale]` (mirroring how `/login`/`/register`/etc. already work), removing `/candidate` from `middleware.ts`'s `EXCLUDED_PREFIXES`.
  - Update every existing `redirect("/candidate/...")` call site across the codebase (there are many — every recruiter/admin/candidate page that redirects a non-candidate away, every server action that redirects post-submit) to be locale-aware, following the exact pattern already established for the auth pages during the original i18n phase.
  - Per the hard-won constraint already on record in this project's memory (`i18n_architecture_gotchas`): `NextIntlClientProvider` must live inside the `[locale]` segment's layout, not the root layout, or client components and `<html lang/dir>` go stale on locale switch — the candidate layout migration must follow this exactly, not rediscover it.
  - New translation namespaces for every existing candidate page (`Candidate.Dashboard`, `Candidate.Profile`, `Candidate.Resume`, `Candidate.Applications`, `Candidate.Jobs`, `Candidate.ResumeBuilder`, etc.) in `messages/{en,ar}.json`, plus an RTL audit of every existing candidate component (physical-direction Tailwind classes → logical properties, the same pass already done for public pages in the original i18n phase).
**UI/UX:** no visible functional change to existing features — same pages, same behavior, now locale-prefixed and translated.
**Security:** none.
**Performance:** none beyond the existing, already-proven cost of locale-prefixed routing elsewhere in the app.
**Scope estimate:** **Large** — this is a real, standalone migration project in its own right (every existing candidate page + every new one), not a small addition. Sizing it honestly here is the point: it's cheaper as one prerequisite pass than as eight separate retrofits.

### 3.3 "API additions" means Server Actions, not a public REST API

The approved SaaS roadmap sequences a public API *after* Billing, Team Management, Permissions, and Enterprise — building one now would be an architectural deviation from the approved blueprint (an explicit stop condition). Every "API addition" in this proposal is a new Next.js Server Action (`"use server"`, the pattern every existing feature uses), not a new public HTTP endpoint.

### 3.4 Reuse-first discipline (binding engineering rule, not a preference)

**No feature in this proposal introduces a duplicate AI prompt, a duplicate OpenAI call, a duplicate database structure, or a duplicate UI flow for something that already exists.** Where a unit needs a capability another unit or an already-shipped feature already has, it calls that existing function/table/component — it does not re-implement a parallel version "for its own use." Concretely, and non-exhaustively: the rewriter/achievement/bullet/tailoring tools in Unit B are decompositions and extensions of `resume-improver.ts`'s existing prompt and schema shape, not parallel reimplementations; the Skills Gap Analyzer in Unit D reuses `job_matches.missing_skills` rather than re-deriving skill gaps from scratch; the Portfolio Generator in Unit F reuses the dormant `portfolio_items` table rather than a new one; Unit A's Resume Intelligence hub (Section 5) reads from `job_matches` and `interviews` rather than re-scoring match quality or re-deriving interview readiness. Any implementation that finds itself writing a second version of an existing prompt, schema, or query should stop and reuse the first one instead — this is a hard rule for this expansion, not a stylistic default.

| Order | Build unit | Why here |

## 5. Build units — detail

Each unit below covers: what it consolidates from the 24-item target list, database changes, AI architecture changes, UI/UX changes, security implications, performance considerations, and a scope estimate. "API additions" per Section 3.3 means Server Actions throughout, so it isn't repeated as its own line per unit.

### Resume Intelligence — one unified experience, not four disconnected tools

**Decision (binding):** ATS scoring, resume improvement, resume-to-job matching, and interview readiness are **one connected "Resume Intelligence" experience**, not four separate AI tools a candidate has to visit different pages to discover. Concretely, Units A (Score/Health), B (Writing Tools), C (Versioning/History), and G (Heatmap) below are not four standalone pages — they are modules within a single Resume Intelligence hub (e.g. elevating the existing `/candidate/resume` page into this hub, rather than adding a fifth disconnected page next to it), and that hub also surfaces — as connected context, not as separate re-fetched widgets — the candidate's existing job-match quality (`job_matches`, already built) and interview readiness (`interviews`, already built). A candidate opening this hub sees one narrative: *here's your resume's health, here's what to improve, here's how it's matching to real jobs, here's how interview-ready you are* — not four unrelated tools that happen to share a `candidate_id`.

This directly reflects the reuse-first rule in Section 3.4: matching and interview data are **surfaced**, not **re-derived** — the hub reads `job_matches`/`interviews`/`ats_scores`/`resume_suggestion_events` (Unit C) as its data sources, adding no parallel scoring or matching logic of its own.

### Unit H — Application & Interview Tracking polish
**Consolidates:** Application Tracker, Interview Progress Tracker.
**DB changes:** none.
**AI changes:** none — this is pure UI work over existing data.
**UI/UX:** a kanban-style stage view for `/candidate/applications` (grouping by status instead of a flat list); a dedicated `/candidate/interviews` view aggregating every scheduled/completed interview across all applications (today this only surfaces inline per-application).
**Security:** none beyond existing RLS (already candidate-scoped).
**Performance:** trivial — same queries, different presentation.
**Scope estimate:** Small (1 focused phase).

### Unit A — Resume Intelligence Suite
**Consolidates:** AI Resume Score Dashboard, ATS Compatibility Scanner (enhancement), Resume Health Report, general Resume Keyword Gap Analysis.
**DB changes:** none required for the dashboard itself. Optional: a lightweight `ats_score_history` view (or just querying `ats_scores` over time, since every re-scan already inserts a new row) to show trend — likely no new table needed, just a new query.
**AI changes:** extend `ats-scorer.ts`'s schema with a few real *structural* checks that don't need an LLM at all (file format, presence of standard section headers, contact-info parseability, excessive-length flag) — computed in code, not prompted — genuinely closing the "LLM opinion vs. real ATS behavior" gap noted in Section 2, and cheaper than an extra AI call.
**UI/UX:** the "Score & Health" module of the Resume Intelligence hub (see above) — the existing `AtsScoreCard` data plus the new structural checks and a trend view across past scans, not a separate standalone page.
**Security:** none new — same candidate-owned data.
**Performance:** the structural checks are synchronous/local (cheap); no new AI-cost surface.
**Scope estimate:** Small–Medium.

### Unit B — Modular AI Writing Tools
**Consolidates:** AI Resume Rewriter, Achievement Generator, Bullet Optimizer, Resume Tailoring for a Job Description, Cover Letter Generator.
**DB changes:** none for the rewriter/achievement/bullet tools (still ephemeral, same as today, until Unit C adds persistence). Cover letter generation writes into the existing, already-present `cover_letters` table (currently unused for AI content).
**AI changes:**
  - Split `resume-improver.ts`'s single bundled call into three independently callable functions sharing its existing prompt scaffolding: a summary/full rewriter, a per-entry achievement generator, and a per-bullet optimizer — each independently testable, per the standing engineering rule.
  - A new **tailoring mode**: accepts a target job description's text (pasted, or pulled from an existing `jobs` row when tailoring toward a PRA-listed job) alongside the resume, and produces JD-specific rewrite suggestions — directly reuses `job-matcher.ts`'s existing `buildJobText()` helper and `resume-improver.ts`'s candidate-text framing, so this is additive, not a new pipeline.
  - A new `generateCoverLetter()` function reusing the same job-text/candidate-text builders, in the same structured-output style as every other AI module (`candidate-message-drafter.ts` is the closest existing analog to model it on).
**UI/UX:** the "Improve & Write" module of the Resume Intelligence hub — each tool keeps its own small, focused entry point within that module (matches "every feature must be modular") rather than one big "Improve" dialog, plus a "Tailor to this job" entry point on job detail pages that opens straight into the same module with the target job pre-filled.
**Security:** cover letters remain candidate-owned (existing RLS pattern already covers `cover_letters`).
**Performance:** each tool is one OpenAI call, same cost class as existing features; no batch/bulk operations introduced.
**Scope estimate:** Medium.

### Unit C — Resume Versioning & History
**Consolidates:** Resume Version Management, Resume Improvement History, Resume Version Comparison (depends on this unit), AI Suggestions Timeline (depends on this unit).
**DB changes:** this is the one unit with real new schema:
  - A `resume_suggestion_events` table (candidate_id, resume_id or draft_id, section/field, suggestion_type, ai_output jsonb, status: pending/accepted/rejected, created_at) — a durable log of every AI suggestion ever made and its outcome, across *both* existing resume systems (the upload-based improver from Unit B and the existing Resume Builder's per-section suggestions) rather than a third parallel mechanism.
  - A lightweight `resume_versions` concept: either a `label`/`tailored_for_job_id` nullable pair of columns added to the existing `resume_drafts` table (cheapest option, reuses the system that already has section-level structure) or a new join table if a resume needs multiple named snapshots — the cheaper column-addition approach is recommended unless real usage shows a need for more than "one draft = one version."
**AI changes:** none new — this unit is persistence/UI over Units A/B's outputs.
**UI/UX:** the "History & Versions" module of the Resume Intelligence hub — a version list/selector, a side-by-side diff view between two versions (Resume Version Comparison), and a chronological feed reading from `resume_suggestion_events` (AI Suggestions Timeline). The timeline is a natural, cheap extension of the audit-log pattern already planned platform-wide in the SaaS blueprint's Section 3.5, just scoped to a candidate's own resume activity instead of company-wide security events.
**Security:** `resume_suggestion_events` needs the same owner-only RLS shape as every other candidate table (`candidate_id = auth.uid()`).
**Performance:** append-only event table, indexed by `(candidate_id, created_at)` — cheap to query and to grow.
**Scope estimate:** Medium–Large (the only unit with a real migration and a genuinely new persistence model).

### Unit D — Career Growth Tools
**Consolidates:** Skills Gap Analyzer (general), AI Career Coach, AI Career Roadmap.
**DB changes:** none required for the Skills Gap Analyzer (reads existing `job_matches`). Career Coach/Roadmap: a small `career_goals` table (candidate_id, target_role, target_industry, notes) if the candidate should be able to set an explicit target rather than only reacting to job matches — needed for a *roadmap* to mean anything beyond "your gaps vs. jobs you've already seen."
**AI changes:**
  - `analyzeSkillsGap()`: aggregates `missing_skills` across a candidate's recent `job_matches` (or against a stated target role) into a single ranked view — no new AI call needed for the aggregation itself, only for a short "what to learn first and why" narrative.
  - `generateCareerRoadmap()`: given the candidate's profile + stated target (or their strongest match trend if no target is set), produces a staged plan (skills to learn, suggested next-role types, rough timeline) — structured output, same pattern as every other AI module.
  - AI Career Coach: recommend a **structured Q&A** interaction (candidate picks from a small set of common career questions, or asks a free-text question scoped to their own profile+application data) rather than an open-ended chat — open-ended conversational UI is a much bigger UX/moderation surface, and a structured version delivers most of the value at a fraction of the risk and cost for a first version.
**UI/UX:** a new `/candidate/career` area with three related but distinct views (gap analysis, roadmap, coach) — kept as separate modular pages/components even though they share a section, not one monolithic "career" screen.
**Security:** standard candidate-owned data; the coach's free-text input should be scoped/prompted to only reason about the candidate's own stored profile/application data, not arbitrary open-ended requests.
**Performance:** roadmap/coach responses are naturally longer AI calls (more output tokens) — worth noting as a real, if modest, cost difference from the shorter existing AI features, relevant once metering (Section 3.1) is wired up.
**Scope estimate:** Medium (gap analyzer) + Large (coach/roadmap, due to new UX pattern).

### Unit F — Personal Brand Tools
**Consolidates:** Personal Portfolio Generator, LinkedIn Profile Optimizer, Recruiter View Simulation.
**DB changes:** Portfolio Generator reuses the existing, currently-unused `portfolio_items` table as-is; needs one addition — a public-visibility toggle and a slug on `candidates` (e.g. `portfolio_slug`, `portfolio_is_public`) to support a shareable public page. LinkedIn Optimizer and Recruiter View Simulation need no new schema (ephemeral analysis, same shape as the existing improver).
**AI changes:**
  - Portfolio Generator: assembles a public page from existing profile + experience + `portfolio_items` data, with AI only used for a short generated summary/headline — not for fabricating portfolio content.
  - LinkedIn Profile Optimizer: candidate **pastes** their LinkedIn "About"/experience text (never scraped or fetched from a LinkedIn URL — LinkedIn's terms of service prohibit automated scraping, so this must be a paste-in tool, the same posture TopResume itself effectively takes) → reuses the same structured-critique shape as `resume-improver.ts`.
  - Recruiter View Simulation: reuses `runAIScreening`'s existing evaluation dimensions, reframed as "here's a recruiter's likely first impression," rather than a new scoring model.
**UI/UX:** the Portfolio Generator is the one feature needing a **new public route** (e.g. `/portfolio/[slug]`), off by default (opt-in, mirroring the `is_open_to_work` opt-in precedent from the AI Resume Matching phase) — a real, if small, new surface area to secure correctly.
**Security:** the public portfolio route must only ever expose what the candidate explicitly marked public — same discipline as the opt-in discoverability RLS work already shipped. LinkedIn paste-in content is treated exactly like resume text (candidate-owned, never shared elsewhere).
**Performance:** portfolio pages should be cacheable/ISR-friendly (public, rarely-changing content) — consistent with the existing ISR pattern already used for `/jobs`, `/companies/[slug]`.
**Scope estimate:** Medium (portfolio needs the new public-route security work; the other two are smaller, ephemeral-analysis tools).

### Unit G — Resume Heatmap
**Consolidates:** Resume Heatmap.
**Important framing note:** there is no real eye-tracking data available — this must be built as an **AI-estimated attention model** (e.g., using density of quantified achievements, keyword relevance, and section prominence as a heuristic proxy for where a recruiter's attention would land), clearly labeled as an estimate, not a claim of real recruiter behavior data. Flagging this now so expectations are set correctly rather than implied by the name alone.
**DB changes:** none — derived, ephemeral output over existing parsed resume data.
**AI changes:** one new function producing a per-section/per-line "attention weight" score, reusing the same `ParsedResumeData` shape every other resume AI feature already consumes.
**UI/UX:** the "Heatmap" module of the Resume Intelligence hub — a visual overlay on the resume content (color-coded by attention weight) — the most novel *rendering* work in this proposal, though not novel AI work.
**Security:** none beyond standard candidate-owned data.
**Performance:** one AI call per generation, same cost class as existing features.
**Scope estimate:** Small–Medium (mostly a visualization/rendering effort).

### Unit E — Salary Insights
**Consolidates:** Salary Insights.
**Decision (resolved):** **no external salary-data provider in v1.** AI generates estimated salary ranges only, always rendered with a clear, unmissable disclaimer that the figures are AI estimates, not market-verified data. The architecture is **provider-agnostic** by design, so a licensed data provider can be added later purely as a new implementation behind an existing interface — never a redesign.
**Provider-agnostic architecture, concretely:** a `SalaryInsightsProvider` interface (`getSalaryEstimate(role, location, experienceLevel, ...) → { min, max, median, currency, source: 'ai_estimate' | <provider name>, confidence, disclaimer }`) with exactly one implementation for v1 — an AI-estimate provider reusing the same candidate/job text-building helpers every other AI module already uses. Every call site (the standalone tool and the inline job-detail-page surfacing) calls the interface, never the concrete AI implementation directly — so adding a real provider later means writing a second implementation of the same interface and switching which one is wired up, with zero changes to any calling code. This mirrors the same "swap the implementation, not the contract" discipline already used for the SaaS blueprint's `metric_key` namespace and `has_capability()` model.
**DB changes:** none for v1 (no credentials/config to store since there's no external provider yet).
**AI changes:** one new function (the AI-estimate provider implementation) producing a salary range + confidence + disclaimer for a role/location/experience level.
**UI/UX:** surfaced both standalone (a dedicated tool) and inline on job detail pages (next to a specific listing's stated range, where one exists) — the disclaimer is part of the shared display component, not something each call site has to remember to add.
**Security:** none beyond standard candidate-owned data (no external credentials to protect in v1).
**Performance:** one AI call per estimate, same cost class as existing features.
**Scope estimate:** Small.

## 6. What this proposal deliberately does not include

- **Auto Apply** (TopResume has it; not on the user's target list, and carries real ToS/legal risk against third-party job boards) — explicitly out of scope, not a silent omission.

## 8. Future compatibility — reserving architecture for what comes after this proposal

Five named future AI capabilities need to slot into this architecture later **without a redesign**: **AI Career Coach**, **AI Career Roadmap**, **AI Learning Recommendations**, **Recruiter Feedback Insights**, and **Workforce Skills Intelligence**. Two of these (Career Coach, Career Roadmap) are already part of Unit D above, not deferred — they're included in this proposal's own scope. The other three are explicitly *not* being built now, but the design choices already made across this document and the approved SaaS blueprint are what make them addable later without restructuring:

- **AI Learning Recommendations** (what a candidate should learn next, and from where) is a direct extension of Unit D's `analyzeSkillsGap()`/`generateCareerRoadmap()` output — those functions already produce "skills to learn" as structured data; a learning-recommendations feature consumes that same structured output and adds a recommendation layer on top, rather than needing its own skills-gap logic.
- **Recruiter Feedback Insights** (aggregating interview feedback/hiring outcomes into insights, likely surfaced to candidates and/or recruiters) reads from `interviews.feedback`/`star_evaluation`/`competency_ratings` and `screening_results` — data that already exists from the AI Interview Assistant and screening pipelines. Adding this later is a new query + AI-summarization layer over existing tables, not new data collection.
- **Workforce Skills Intelligence** (aggregate, cross-candidate/cross-company skill trend analysis) is the same future capability already named in the approved SaaS blueprint's own Section 5 ("AI Workforce Analytics") — this proposal doesn't introduce a second, competing extensibility mechanism for it. Both documents point at the same mechanism: the SaaS blueprint's open `metric_key` namespace (for metering/entitlements) and capability-based gating (`has_capability()`) already accommodate a new AI service by adding a new metric key and capability string, not by changing the entitlement/permission architecture itself.
- More generally: every AI module in this proposal is written as the same shape as every existing one — a single-purpose function in `src/lib/ai/`, taking structured input and returning structured (Zod-validated) output, callable independently of any specific UI. That shape is what makes each of these five future items addable as a new function plus a new capability/metric key, not a new architecture.
