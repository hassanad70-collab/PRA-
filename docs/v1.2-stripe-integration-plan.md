# Stripe Integration Plan (v1.2 Billing — Design Only)

**Status:** Approved — official Billing Architecture Blueprint. No implementation code has been written against this plan.
**Depends on:** `docs/v1.2-saas-architecture-proposal.md` (the approved SaaS Architecture Blueprint), specifically Section 2 (Subscription & Billing). This document makes that section concrete enough to implement, and goes no further than that scope.
**Prerequisite before implementation starts:** a Stripe account (test mode is enough to begin), API keys, and a webhook signing secret, to be provided by the user once this plan is approved.

---

## 1. Required Stripe products and services

| Stripe capability | Used for | Recommendation |
|---|---|---|
| **Stripe Billing** (Products, Prices, Subscriptions, Customers) | Core subscription plumbing | Required — this is the foundation everything else sits on. |
| **Stripe Checkout** (hosted) | Collecting a payment method + starting a subscription | Use hosted Checkout, not embedded Stripe Elements, for v1. Less PCI scope, no custom payment-form code, faster to ship. Embedded Elements can replace this later if a more branded in-app flow is wanted — not needed to start. |
| **Stripe Customer Portal** (hosted) | Upgrade/downgrade, payment method updates, invoice history, cancellation | Use Stripe's hosted Portal instead of building custom UI for these flows (Sections 9–10). Free, PCI-compliant, and Stripe already solved the proration/scheduling edge cases correctly. |
| **Stripe Webhooks** | Syncing subscription/payment state back into our database | Required — our DB must never be the source of truth for subscription state; it mirrors what Stripe reports. |
| **Stripe Billing Meters / usage records** (metered billing) | Reporting AI-credit overage for invoicing | Used only for *invoicing* overage, not for real-time gating (Section 7 explains why those are two different systems). |
| **Stripe Tax** | Automatic sales tax/VAT calculation | Not included in v1. This is a business/legal decision (which jurisdictions we have tax nexus in) that hasn't been made — flagging it here so it isn't forgotten, not deciding it now. |
| **Stripe CLI** | Local development, webhook forwarding | Required for local dev (Section 14). |

No client-side Stripe.js/Elements library is needed for v1 — hosted Checkout and Portal work entirely via server-side session creation + redirect, which also means no `STRIPE_PUBLISHABLE_KEY` has to be exposed to the browser at all unless a later phase adds embedded payment UI.

## 2. Subscription architecture

- **One Stripe Customer per company**, never per recruiter — matches the blueprint's ownership model (Section 3.6: billing is owned at the org level). A new `companies.stripe_customer_id` column is the join key.
- **One Stripe Subscription per paying company**, containing two Subscription Items on the same subscription (not two separate subscriptions, so Stripe invoices them together):
  1. A **licensed** (per-seat) recurring Price — quantity = current active recruiter count.
  2. A **metered** recurring Price — AI-credit overage, reported via usage records (Section 7).
- **Free-tier companies get no Stripe objects at all.** No Customer, no Subscription. A company only gets a Stripe Customer created at the moment it actually starts a paid plan via Checkout. This keeps Stripe's data clean (no placeholder objects for companies that never pay) and avoids modeling a "$0 subscription" that has no real purpose.
- **Enterprise** is still modeled as a real Stripe Subscription with custom Prices created per deal (for consistent invoicing/reporting), not necessarily handled outside Stripe — unless a specific deal is bespoke enough to need offline invoicing, which would be a case-by-case call, not a default.

## 3. Products and Price IDs structure

- One Stripe **Product** per paid tier: "PRA Growth", "PRA Business" (Free has no Product; Enterprise uses custom Prices, optionally under a shared "PRA Enterprise" Product).
- Each paid-tier Product has exactly **two Prices**:
  - A recurring **licensed** Price (per seat/month) — subscription item `quantity` tracks seat count.
  - A recurring **metered** Price (AI-credit overage) — `usage_type: metered`, aggregated via Billing Meters.
- **v1 ships monthly billing only.** Annual pricing (a second Price per tier, at a discount) is a reasonable fast-follow, not included now — flagging this as a scope decision rather than silently deciding it, since it affects how many Price IDs need to exist.
- **Single currency (USD) for v1.** Multi-currency is a real feature (separate Price per currency) but there's no evidence of international pricing need yet — deferred, not decided against.
- Price IDs are **environment-specific** — Stripe test mode and live mode are two separate data sets with different IDs for what is conceptually "the same" price. Price IDs must never be hardcoded in application code.
  - Recommendation: store them as environment variables (`STRIPE_PRICE_GROWTH_SEAT`, `STRIPE_PRICE_GROWTH_AI_OVERAGE`, `STRIPE_PRICE_BUSINESS_SEAT`, `STRIPE_PRICE_BUSINESS_AI_OVERAGE` — see Section 13), not a database table. For a small, fixed set of tiers, env vars are simpler than a table, avoid needing a migration to change a price, and match this project's existing convention for external-service configuration (`OPENAI_API_KEY`, the Supabase keys).
  - This is deliberately kept **separate** from the blueprint's `plan_defaults` table, which describes entitlement *amounts* (how many AI credits, how many seats), not billing *SKUs*. Keeping "what a plan includes" and "what Stripe object bills for it" as separate concerns matches this project's existing separation-of-concerns discipline (e.g., query layer vs. action layer).

## 4. Webhook architecture

- **Single endpoint:** `POST /api/webhooks/stripe` (a Next.js Route Handler, same shape as the existing `/api/web-vitals` route).
- **Raw body required.** Signature verification needs the exact raw request bytes — the handler must read `await request.text()`, not a parsed JSON body, before calling `stripe.webhooks.constructEvent(rawBody, signature, STRIPE_WEBHOOK_SECRET)`. Any event that fails verification is rejected (400) and never processed.
- **Idempotency is mandatory.** Stripe can and does deliver the same event more than once. A new `processed_stripe_events` table (`event_id` primary key) records every event handled; the handler checks this first and returns 200 immediately for an already-processed event, before any side effect runs. Without this, a duplicate `invoice.paid` event could double-grant credits or double-log an audit entry.
- **Events handled, and what each does to our DB:**

| Event | Effect |
|---|---|
| `checkout.session.completed` | First-time plan selection: store `stripe_customer_id`/`stripe_subscription_id` on `companies`, set `plan_tier`, activate entitlements. |
| `customer.subscription.updated` | Plan tier changed, seat quantity changed, or status changed (active/past_due/canceled/trialing) — sync onto `companies.plan_tier` / `companies.subscription_status`. |
| `customer.subscription.deleted` | Subscription actually ended (immediate cancel, or a scheduled period-end cancellation reaching its end) — downgrade the company to Free tier. Data is retained, never deleted. |
| `invoice.payment_failed` | Mark `subscription_status = 'past_due'`, log to `audit_logs`, surface an in-app banner (Section 11). |
| `invoice.payment_succeeded` | Clear `past_due`, log to `audit_logs`. |

- **Unrecognized customer handling:** if a webhook references a `stripe_customer_id` we don't have on file (e.g., Stripe's dashboard "send test webhook" button, or a race during setup), log it and return 200 — never 500/retry-loop on an event we can't act on.
- **All webhook DB writes go through the admin/service-role Supabase client** (`createAdminClient()`, already used everywhere else in this codebase for privileged/system writes) — a webhook request has no user session to act as.
- **Billing-relevant transitions are audit-logged** via the existing `logAuditEvent()` helper (`src/lib/audit.ts`), per the blueprint's Section 3.5 requirement that billing changes are a security-sensitive action.

## 5. Customer lifecycle

1. **Company created** (`registerRecruiter`) → no Stripe object yet. Trial starts entirely in our own database (Section 6).
2. **Company subscribes** (during or after trial) → create a Stripe Customer if none exists → redirect to a Checkout Session for the selected plan → on `checkout.session.completed`, store the customer/subscription IDs and activate the plan.
3. **Ongoing seat changes** (teammate invited/removed) → the corresponding `team.ts` action also updates the Stripe subscription item's `quantity` in real time (Section 8) — Stripe stays in sync as it happens, not via a periodic reconciliation job.
4. **Company churns** → subscription canceled (Section 10) → `customer.subscription.deleted` fires at the actual end of the paid period → downgrade to Free, retain data.
5. **Payment fails repeatedly** → Stripe's own Smart Retries run their course → if exhausted, Stripe transitions the subscription to `canceled`/`unpaid`, which we mirror (Section 11).
6. **Reactivation** → a churned or downgraded company can start a fresh Checkout Session at any time; there's no special "win-back" path needed since Free-tier data was never deleted.

## 6. Trial handling

**Trial state lives entirely in our own database — not in Stripe.** This is a deliberate architectural choice, not an oversight:

- The blueprint's trial is card-optional. Stripe subscriptions are built around eventually charging a card; modeling a card-less 14-day trial as a real Stripe Subscription (with `trial_period_days` and no payment method) adds real complexity — `trial_settings.end_behavior` for the no-card case, subscriptions existing for companies that may never pay — for no benefit, since we're not using Stripe for anything during the trial anyway.
- Instead: `companies.trial_ends_at` is set at company creation (`now() + 14 days`). `getCompanyEntitlements()` already has to check plan state on every gated action; it checks this column the same way.
- **Trial expiry is an explicit write, not only a lazy computed check.** A daily scheduled job flips `companies.plan_tier` from `'trial'` to `'free'` once `trial_ends_at` has passed. Relying purely on "compute it lazily every time it's checked, forever" risks a future code path that reads `plan_tier` directly instead of through the proper resolver and gets it wrong — an explicit, auditable state transition is safer, with the lazy check remaining only as a defensive fallback.
- **Converting to a paid plan during the trial ends the trial immediately** — the new Checkout Session starts a normal paid subscription from day one, with **no `trial_period_days` set on the Stripe subscription itself**. The in-app trial already happened; layering a second, Stripe-side trial on top would just create confusing double-trial semantics.

## 7. AI credit metering

Two systems, two different jobs — important not to conflate them:

- **Real-time gate (ours): `usage_counters`.** Every AI-generating action (screening, matching, interview-question generation, job-description drafts, candidate-message drafts, resume-builder suggestions) calls a single shared `consumeAiCredits(companyId, amount = 1)` helper *before* calling OpenAI — checking cost before spending it, not after. This helper resolves the company's entitlement (plan default or override, per the blueprint's Section 2.2 design), checks the current billing period's counter, and:
  - Under the cap → increment and allow.
  - Over the cap, on a paid plan with overage billing configured → still allow, but flag the unit as *overage* for later Stripe reporting.
  - Over the cap, no overage billing available (Free tier, or no payment method on file) → hard block, per the blueprint's "AI credits are the one resource where a hard stop is non-negotiable."
- **Invoicing (Stripe's): Billing Meters / usage records, reported in batches.** Overage units are *not* reported to Stripe synchronously on every AI call — that would add a third-party network round-trip to the hot path of every AI feature, and Stripe's meter API is designed for aggregate reporting, not per-event calls. Recommendation: a nightly job sums each paying company's over-allotment usage for the current period and reports it once.
- **Period alignment:** for a company with an active Stripe subscription, `usage_counters` resets in sync with that subscription's actual `current_period_start`/`current_period_end` (captured off the subscription webhook), not a fixed calendar month — so metering matches what's actually being billed.

## 8. Seat management

- Seat count = the number of active `recruiters` rows at a company (already queryable via the existing `getCompanyMembers()`).
- The Stripe subscription's licensed Price carries this as its `quantity`.
- **`acceptInvite`** (when a new member joins) and **`removeMember`** (existing actions, from the Organizations & Roles phase) each get a new responsibility once Billing ships: call Stripe's subscription-item update API to adjust `quantity` immediately after the DB write succeeds. If the Stripe call fails, the invite/removal itself still succeeds (never block a human joining or leaving a team on a third-party API hiccup) — the mismatch is logged for reconciliation rather than surfaced as a user-facing error.
- **Seat limits are enforced by our own entitlement check, not by Stripe.** `createInvite` checks the current member-plus-pending-invite count against the plan's seat entitlement *before* creating the invite (per the blueprint's "hard block on invite beyond plan limit") — Stripe's `quantity` is kept in sync for accurate billing, but is never itself the gate.
- Mid-cycle seat changes are prorated using **Stripe's default proration behavior** (`create_prorations`) — no custom proration math, for v1 simplicity.

## 9. Upgrade/Downgrade flow

- Handled through the **Stripe Customer Portal**, not custom in-app UI. Our app's part: an Owner-only "Manage billing" action (gated by the `manage_billing` capability from the Organizations & Roles phase) that creates a Portal session and redirects there. Stripe's hosted UI handles the actual plan switch and any proration math; we only listen for the resulting `customer.subscription.updated` webhook to sync `plan_tier` back.
- **Upgrades take effect immediately**, prorated for the remainder of the period (Stripe's default).
- **Downgrades take effect at the end of the current billing period**, not immediately — configured in the Stripe Dashboard's Customer Portal settings, no custom code required. This avoids clawing back access mid-period from something already paid for.
- **Seat-limit downgrade policy (resolved):** if a company downgrades to a tier with a lower seat limit while currently having more active members than the new limit allows:
  - The downgrade is **always allowed immediately** — never blocked.
  - This starts a **14-day grace period**, tracked via a new `companies.seat_grace_period_ends_at` timestamp (set to `now() + 14 days` the moment the company's active seat count is found to exceed its new entitlement).
  - **During the grace period, no new members can be invited, and no removed/former member can be reactivated**, while the company remains at or over its seat limit. This is enforced the same way seat limits already are (Section 8: our own entitlement check, not Stripe) — `createInvite`, and any future "reactivate a removed member" action, must check both the plan's seat entitlement *and* whether an active grace period plus over-limit condition applies.
  - **Existing members keep full access throughout, with no exceptions.** Nothing about this policy ever removes, disables, or degrades an existing user's access — the only thing blocked is *adding* seats while over limit.
  - **At the end of the grace period**, if the company is still over its seat limit, still nothing is automatically removed or disabled — the invite/reactivation block (already in effect since the grace period began) simply continues indefinitely until the company either removes members down to the limit or upgrades again. The 14 days is a deadline for the company to act, not a trigger for us to act on their behalf.
  - The grace period clears (`seat_grace_period_ends_at` reset to `null`) the moment the company's active seat count drops to at or under its current entitlement — whether that happens by removing members or by upgrading.

## 10. Cancellation flow

- Also handled via the **Customer Portal** — "Cancel subscription" is built in.
- **Cancellation takes effect at period end** (`cancel_at_period_end: true`), not immediately — matches the blueprint's "graceful downgrade, not lockout" philosophy; the customer keeps what they already paid for through the period they paid for.
- On `customer.subscription.deleted` (firing once the canceled subscription actually reaches its period end) → downgrade to Free tier, retain all data.
- **Reactivation before period end** ("I didn't mean to cancel") is already supported by the Portal's built-in "renew subscription" action — no custom code needed.
- **No exit-survey/win-back flow in v1** — a real feature, but not a blocker, and out of scope for this pass.

## 11. Failed payment recovery

- **Stripe Smart Retries** (configured in the Dashboard) handle the actual retry schedule and attempts — no custom retry logic is built.
- On `invoice.payment_failed`: set `companies.subscription_status = 'past_due'`, log via `logAuditEvent`, and show an in-app banner (visible to Owner/Admin) prompting a payment-method update, linking to the Customer Portal.
- **No hard lockout on the first failed charge.** Access continues (with the banner visible) through Stripe's retry window — full downgrade to Free only happens once Stripe actually exhausts retries and cancels/marks the subscription unpaid, mirrored via the same `customer.subscription.deleted`/`updated` handling already described.
- **Dunning emails: rely on Stripe's own built-in payment-failure emails**, configured in the Dashboard, rather than building custom notification emails. This project has no general email-sending infrastructure yet (a recurring note across prior phases); Stripe's own emails give real customer-facing billing communication without that infrastructure needing to exist first.

## 12. Security considerations

- **Webhook signature verification is non-negotiable** (Section 4) — an unverified event is never processed, full stop.
- **`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are server-only** — never in a `NEXT_PUBLIC_*` variable, never sent to the client. Since v1's hosted-redirect design needs no client-side Stripe.js, there may be no Stripe key exposed to the browser at all.
- **Every billing-mutating server action is capability-gated** (`manage_billing`) using the same `requireCapability()`-style pattern already established in `src/actions/team.ts` — only the Owner role has this capability per the blueprint's seed data.
- **Idempotency keys** on any Stripe API call that creates an object (e.g., a Checkout Session) to prevent duplicate subscriptions/charges from a double-click or a retried request.
- **Never trust client-supplied pricing.** The actual Stripe Price ID for a Checkout Session is always resolved server-side from our own `plan_tier` mapping (Section 3/13) — never accepted as client input.
- **Rate-limit** the "create Checkout session"/"create Portal session" actions the same way registration and login already are (`rateLimitByIp`), to prevent abuse.
- **Test-mode vs. live-mode key separation** is a hard requirement — covered as its own checklist item in Section 15, since mixing them up is the single most common and most damaging Stripe integration mistake.

## 13. Required environment variables

| Variable | Scope | Purpose |
|---|---|---|
| `STRIPE_SECRET_KEY` | Server-only | Main Stripe API key (`sk_test_...` locally, `sk_live_...` in production). |
| `STRIPE_WEBHOOK_SECRET` | Server-only | Verifies webhook payloads (`whsec_...`); different values for local (`stripe listen` output) vs. the deployed endpoint. |
| `STRIPE_PUBLISHABLE_KEY` | Reserved, likely unused in v1 | Only needed if a later phase adds client-side Stripe.js/Elements. Not required for the hosted-redirect design this plan recommends. |
| `STRIPE_PRICE_GROWTH_SEAT`, `STRIPE_PRICE_GROWTH_AI_OVERAGE` | Server-only | Price IDs for the Growth tier (Section 3). |
| `STRIPE_PRICE_BUSINESS_SEAT`, `STRIPE_PRICE_BUSINESS_AI_OVERAGE` | Server-only | Price IDs for the Business tier. |

`NEXT_PUBLIC_SITE_URL` (already exists) is reused as-is for Checkout/Portal success and cancel redirect URLs — no new variable needed for that. Exact final variable names for the price IDs will be confirmed once tiers/pricing are finalized in the Stripe Dashboard.

## 14. Local development workflow

- **Stripe CLI** (`stripe login`, then `stripe listen --forward-to localhost:3000/api/webhooks/stripe`) forwards real webhook events to the local dev server. The CLI prints its own signing secret to use as the *local* `STRIPE_WEBHOOK_SECRET` — this is different from the secret configured for the deployed production endpoint in the Dashboard.
- **Test mode only, everywhere in development** — test-mode API keys, test-mode Products/Prices, and Stripe's published test card numbers (e.g. `4242 4242 4242 4242`) for exercising Checkout.
- **Playwright/e2e implications:** driving an actual Stripe Checkout redirect through Playwright is unreliable (it leaves our origin, depends on Stripe's live hosted pages, and isn't something we should assert against). Recommended e2e strategy instead:
  - Assert that our "Upgrade"/"Manage billing" actions correctly create a Checkout/Portal session and redirect to a `checkout.stripe.com`/Stripe-hosted URL — without following that redirect.
  - Exercise *our* webhook handler logic directly, either via the Stripe CLI's `stripe trigger <event>` command or by posting a hand-crafted, correctly-signed test event to the local webhook endpoint — verifying our DB updates and entitlement changes react correctly to known event payloads, rather than testing Stripe's own UI.
  - This mirrors the existing accepted pattern in this codebase for OPENAI_API_KEY-gated features: test *our* code's handling of the integration, with the third-party service's own UI/behavior treated as out of scope for our test suite.
- `.env.local` holds test-mode values; `.env.example` documents the required variable names with placeholder values, matching this project's existing convention.

## 15. Production deployment checklist

- [ ] Stripe account created and business verification completed (required before accepting live payments).
- [ ] Live-mode Products/Prices created in the Stripe Dashboard, mirroring the test-mode setup exactly — test and live mode are entirely separate data sets; nothing carries over automatically.
- [ ] Live webhook endpoint configured in the Dashboard, pointing to the production URL (`https://<production-domain>/api/webhooks/stripe`), subscribed to *only* the event types actually handled (Section 4) — least-privilege on webhook subscriptions.
- [ ] The live endpoint's signing secret copied into Vercel's **production** environment variables as `STRIPE_WEBHOOK_SECRET`.
- [ ] All `STRIPE_*` environment variables in Vercel's production environment double-checked to be **live-mode** values — never test-mode keys in production, and vice versa.
- [ ] Customer Portal settings configured in the Dashboard (which plans are switchable, downgrade/cancellation timing) *before* going live, matching the decisions in Sections 9–10.
- [ ] Smart Retries / dunning email schedule configured in Dashboard settings (Section 11).
- [ ] The billing-related migration (new `companies` columns, `processed_stripe_events`, price-ID wiring) applied to production Supabase, per the standing production-safety rule, *before* deploying any billing code.
- [ ] End-to-end smoke test against the live webhook endpoint (a real, small, refundable transaction, or Stripe's live-mode test clocks) before announcing Billing is live.
- [ ] Spot-check in production that a non-Owner genuinely cannot reach any billing-mutating action.
- [ ] Confirm webhook delivery visibility (Stripe's Dashboard already shows delivery logs/retries) — a dedicated failure alert is a reasonable future addition, not a hard requirement for launch.
